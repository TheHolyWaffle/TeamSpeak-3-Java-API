# Verified global query-login administration

> Current scope: TS3 RAW and SSH only. TS6 functionality and tests are removed.
> Any TS6 observations below are retained historical findings from merged PRs,
> not current support claims or release acceptance requirements.

This focused #441 slice verifies TS3 **3.13.8 RAW** and TS3 **3.13.8 SSH** with the existing pinned fixtures. See the
[overall inventory](command-compatibility.md) and [integration setup](integration-tests.md).

## Verified operations and evidence

`ServerQueryCompatibilityIT.queryLoginDomain` starts an authenticated serveradmin
session with no virtual server selected (`whoami` reports virtual server ID 0).
Each target starts its own disposable server: failed logins can activate server
authentication cooldowns, so negative probes must not share a fixture with other
command tests or transports.
It captures live help for `queryloginadd`, `queryloginlist` and `querylogindel`,
then verifies:

- Global login creation with `queryLogins().create(name, 0)`. The nonpositive
  client database argument is omitted from the command; global context creates
  a new query identity instead of replacing a regular client's login.
- Creation returns a positive server-assigned database ID, `sid=0`, exact name
  and a nonempty password. No fixed ID or password format is assumed.
- The unfiltered list contains the initial entries plus exactly the new login;
  a name-filtered list returns its matching ID, name and global server ID.
- A separate connection uses the generated credentials through the selected
  transport. RAW performs query login; SSH uses transport authentication. Its
  `whoami` identity has the expected login/database ID, origin 0 and no selected
  virtual server; a version command succeeds. No administrative permission grant
  or unrestricted access is inferred from successful authentication.
- The actor closes before deletion. The administrator's cleanup resource deletes
  only the created ID and listing returns to exactly the original rows. The
  administrator remains usable after error probes.
- Repeating deletion returns **512 / `invalid clientID`**. A fresh connection
  using the removed login's formerly valid credentials fails with
  `TS3ConnectionFailedException` and is not connected. Its cause must identify
  authentication rejection: RAW reports **520 / `invalid loginname or password`**,
  SSH reports `UserAuthException`. A timeout or socket failure does not pass.
  Every query and container resource closes
  on failure, and the test has a 60-second deadline.

Create rows contain `cldbid`, `sid`, `client_login_name` and
`client_login_password`; list rows contain the first three fields. The password
is used in memory for the two connection attempts. Reports record creation/list
field names, allowlisted list metadata, authenticated `whoami` output and errors;
they do not record generated password values. Live help includes illustrative
passwords from the server's own examples, not credentials generated by the test.

Reports are saved to `target/compatibility/<target>-query-logins.txt` with existing
version/build/image/transport evidence. Required Docker CI uploads these and test
reports even after failure. The test does not rotate or remove the fixture's
serveradmin login. SQL-like pattern semantics are documented by live help;
acceptance here covers the exercised full name only.

## Release intent and migration

Internal **`test:`** release intent for planned 2.0.0 acceptance. No runtime,
public API, dependency or default changes. For a global identity, create/delete
in a session with no selected virtual server and use the ID returned by that
server. Successful login proves authentication, not a permission role. Handle
actual errors and connection failure after deletion; do not treat a deleted
credential as reusable or a missing identity as an empty administrative result.

A global query identity does not establish a persistent regular client on a
selected virtual server. Positive client/channel-client permissions and other
regular-client behavior remain separate acceptance work. Existing lifecycle,
cancellation and deterministic completion/admission regressions continue to run
in the ordinary unit-test phase; no timing-based shutdown assertion is added.
